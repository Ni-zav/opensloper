# Web version

Part of the [OpenSloper design](../opensloper-design-document.md). Planned, not built beyond a spike. A web version runs in the browser with the same Pascal engine as the desktop apps, compiled to WebAssembly, under a new TypeScript editor, with a Django server for accounts and subscriptions. The site never holds users' files.

**Why it is possible.** The core has no LCL dependency and the Automation API already exposes every document operation as JSON-RPC, so the web needs a new UI, not a new engine, and name rules, formula checks and undo are the same code everywhere.

| Part | Runs in | Language | Does |
| --- | --- | --- | --- |
| Engine | Browser (Web Worker) | Pascal, compiled to Wasm | Core, document and API layers: evaluation, undo, pieces, exports |
| Editor | Browser | TypeScript | Canvas, tools, panels; talks to the engine through the API |
| Server | Server | Python, Django | The editor's files, accounts, subscriptions, simple pages |

The editor runs in the browser: sending every drag to the server would make dragging lag, so the server never takes part in drafting.

**No user data on the site.** Patterns and measurement files stay on the user's machine. Body measurements are personal data under PDPA, and stored files cost hosting, so the server keeps only what an account and a subscription need: a login and an email address, with payment through a provider so no card data is held. Everything the engine does (evaluation, checks, exports) happens in the browser.

## Engine

- **Compiler:** FPC's `wasm32-wasip1` target, only in the development compiler (trunk 3.3.1), so the web build uses a self-built cross-compiler while the desktop stays on the stable one; the core must compile with both, which `opensloper-make.sh test` will check. pas2js was rejected: it has no pointers, which Clipper2 uses.
- **One entry point**, `handle(request) → response`, taking and returning a JSON-RPC message as text, the same as `opensloper-cli serve`. Methods only a canvas needs, named `editor_`, have their own table (`EditorMethods`) in `Sloper.API.EditorServer`, whose `TEditorApiServer` answers them on top of the Automation API. The engine and `opensloper-cli serve` use it, but the editor methods are not MCP tools: a mouse position means nothing to Claude, and its tool list stays short. Methods useful to both editors and automation, such as `open` with contents, go in the Automation API itself.
- **In the module:** `src/core`, `src/document`, `src/editor`, `src/api` and the PDF, SVG and DXF writers. No LCL and no BGRABitmap, so `render` gives SVG only; PNG must be reached through something the module can leave out.
- **Shared editing logic is in `src/editor`** (`Sloper.Editor.*`), a layer without the LCL between the document and the apps, rather than being rewritten in TypeScript or put in `src/core`, which stays the pattern model. The order is core → document → editor → API and UI, and the check forbids the LCL there as in core. As much as possible goes there: the units of `src/ui` that already did without the LCL have moved (Scene, Snap, View, RulerTicks, Completion, ObjectList, Suggestion, SuggestionGrade, SelectionEdits, PanelEdits and PropertyText), and the canvas tools' table (Tools: names, captions, hints, icons and keys) has left `Sloper.UI.CanvasTools`; the logic still inside LCL units follows, the canvas tools' drags and the properties panel's piece and note sections, taken out as the web editor needs it. The properties panel's rows and edits are in `Sloper.Editor.PropertyRows`: which rows an object shows and in what order (`PropertyRows`, by section and place as the desktop's sections build them), the choices' items, the undo names, and the edits as steps on the document; the desktop's sections still build their own controls for those rows, so a row added to one is added to `PropertyRows` too. Layout helpers for desktop widgets (CanvasInput, GridColumns, SideTabsLayout) stay in `src/ui`. What a tool's click makes is `Sloper.Editor.ToolEdits` (a point, a line or curve with its points, a curve carried on, a circle, a rectangle, a piece, a notch added or removed, a seam's sides picked and the seam made, a note, a callout, a callout's tip moved), which the desktop's tools and the editor methods both call; the web editor keeps only a two-click tool's first click and draws the preview. The edge roles' captions (`RoleCaption`) are in `Sloper.Editor.PropertyText`.
- **Label placement is copied too**, as `web/src/editor/labelPlacement.ts`: it is screen arithmetic on every frame with the browser's text sizes, so the TypeScript places the labels with a copy of `Sloper.Core.LabelPlacement` tested with its cases.
- **Behind the API** goes what needs the evaluated pattern: snapping, completion, the object lists, formula suggestions and selection edits. - **Runs in a Web Worker**, so a slow evaluation never freezes the page.

**Spike results** (`web/engine/`, merged into `development` at version 0.7.0). FPC trunk compiles the core, document, API, output and Clipper2 unchanged, with its own Wasm linker. Every regression case gives the same objects, values, states and SVG as the desktop, and layout exports are byte for byte the same. A formula edit with the bodice block's full evaluation takes 3.7 ms in Wasm against 1.7 ms native; the module is 4.3 MB, 570 KB with Brotli. In headless Chromium the engine is ready in about 45 ms and an edit takes 3 to 18 ms at the median, so evaluating on every drag in a worker is affordable. Two fixes were needed: `Sloper.Core.AppPaths` now treats WASI as neither Windows nor Unix, and FPC trunk's WASI `ExpandFileName` doubles a leading `/` (patched locally, to report to FPC).

**Engine size.** A build of the full engine is 4.62 MB, 610 KB with Brotli. Its code is 45% core, 37% RTL and FCL, 10% output, 5% API, 3% Clipper2 and 1% document. The largest library cost, Variants and its helpers (about 200 KB of code), comes with `fpjson`. The linker already leaves out whatever the entry point does not reach, as it does the drape units, so moving units between folders does not change the size. A drafting-only engine could leave out the output units and the font and deflate code they use, with UnitConvert, Garment, Arrange and OutputProfiles: about 620 KB of 3.5 MB of code, some 80 KB after Brotli. That saving does not pay for a second module, a hand-over of the pattern between the two and a wait at the first export, all the more as the offline editor downloads the module only on the first visit and after an update, so **the core is not split**; the engine is one module. Stripping the name section, which `-Xs` leaves in, takes it to 4.14 MB, 540 KB with Brotli, for no change to the code: `opensloper-make.sh web --strip-names` does it, off by default while the engine changes, as the names make a stack trace readable, and to be made the release build's default once the engine is stable.

## Files and storage

The browser has no ordinary filesystem, so the engine does not open files by path: `open` takes the pattern file's `text`, `save` with `text` gives the contents back without writing, and `use_measurements` takes the measurement file's `text` (`TPatternDocument.LoadFromText`, `SaveToText` and `UseMeasurementsText`). A pattern opened from text has no file name and no measurement set; the reply's `measurementsFile` is the reference the pattern stores, which the editor resolves against the pattern's folder and supplies. References between files stay relative paths with `/`, resolved by whoever supplies the file, so a set of files moves between desktop and web unchanged. A set given as text is never read or written on disk, so the file watching skips it, and `ChangeMeasurements` changes it in memory (`TPatternDocument.MeasurementText`), for the editor to save as a download; `set_measurement` refuses it, as its reply could not hand the file back. Files are opened and saved on the user's machine through the File System Access API where the browser has it (Chromium-based browsers; `FileAccess` in `ui/fileAccess.ts`), else by upload and download. With it, Open and Measurements… use the browser's pickers, which start beside the pattern; a pattern saves back to the file it came from (Save, Ctrl+S), and Save as (Ctrl+Shift+S), or Save for a pattern from an example, asks for a file. Its measurement file is found from a folder the user grants once: when the pattern names a file that was not picked with it, the status bar offers Find it…, which asks for the folder (starting at the pattern's), and the folder's handle is kept in IndexedDB, so later the file is found by its path from the pattern (`resolve` gives the pattern's place in the folder) as soon as the pattern opens; a folder the browser has stopped letting the page read is read again from the same button, as asking needs a click. A set chosen with Measurements… is recorded by its path from the pattern when a granted folder holds both, else by its name. The Measurements tab's Save writes to the set's file, found the same way, else chosen; the file is chosen before the edits are made, so cancelling keeps them waiting. Leave to write a file is asked while the user's click still counts, before the engine is. Work in progress is kept in browser storage so a closed tab loses nothing; it never leaves the machine (`Autosave` in `ui/autosave.ts`). A second after each change, while the pattern is not saved, `editor_snapshot` gives the pattern file's text without counting it saved, with the measurement set's text, and both are written to the page's private file system (OPFS) under the tab's own id, with a record in IndexedDB of when, the file name and the handles of the files they came from; where the page cannot write OPFS files (some browsers allow it only in workers) the texts go in the record. Saving removes them. Each tab holds a Web Lock while it is open, so work whose lock is free was left by a tab that closed: on starting, the app offers the newest such work in the status bar, to open again or discard, then the next. Opened again, it is the pattern as it was, counted as not saved (`editor_mark_unsaved`), saving to the file it came from. The Measurements tab's edits waiting in bold are not kept, as they live in the editor server, not the document. Open and Examples ask before replacing a pattern with changes not saved, which the tab's work in progress would otherwise lose. File watching is dropped on the web. File formats do not change.

## Editor

A TypeScript single-page app per job, as on the desktop, sharing one engine module. Drafting comes first, opening measurement files the user supplies; the measurements editor follows on the same structure, then publish. There are no measurement forms on the server. The canvas draws from the computed geometry the engine reports (Canvas2D, WebGL if needed), not from `render`'s SVG. Tools, shortcuts, snapping, undo steps and colours match the desktop, following these design files. Output is written by the engine and downloaded; printing goes through the browser's PDF viewer. **It works offline** as an installable web app: a service worker caches the editor and the `.wasm` file, the only things it fetches, so it installs from the browser and runs without a connection. Built: `sw.js` (`src/design/serviceWorker.ts`) keeps every file of the app (the page, its scripts, the engine, the icons and the guide's examples) in a cache named after the build, and answers from it before the network; the bundler gives it the list of files and a version made from their contents, and starts from an empty `out/design` so no file an older build left is kept. The first worker takes the page over at once. A new build's worker installs beside the running one and waits: an Update button at the toolbar's end reloads into it, writing the work not saved to the browser first, which the reloaded page offers back; the old build's cache goes once the new one takes over. `manifest.webmanifest`, with the app's icon as SVG and as PNGs at 192 and 512 px (`resources/web`, from `make-icons.sh`), lets the browser install it. Registering it is a convenience, so a browser without service workers runs the app as before. Anything a subscription gates is checked when online, with a grace period offline.

Tools, shortcuts and edge role colours and dashes come from `editor_tables`. `PatternDocument` asks `editor_changes` after every call and reloads the scene when the pattern changed; mouse moves go through a latest-only queue, so a slow answer never piles up requests. Notes are drawn in the browser's sans-serif, as the desktop canvas uses the system's font; their boxes come from the engine, which in Wasm has no font files and estimates text widths, so a box may be a little wider or narrower than its text. The TypeScript is one npm project in `web/`, with the spike's page.

**Plain TypeScript, no UI library**, with the structure of the desktop UI copied. Each `src/ui` unit that the web needs becomes a module of the same name (`Sloper.UI.ListPanel` → `ui/listPanel.ts`), with the same classes and hierarchy: a list panel base with the objects, variables and measurements panels; property sections for the properties panel; tool handlers with the snap tool under the point, edge and shape tools; a canvas host. A fix or feature then lands in the same place in both. Names follow TypeScript's conventions (no `T` prefix, camelCase members) but are otherwise unchanged. The differences are kept where the platforms differ:

- **The document is a proxy.** `PatternDocument` in TypeScript sends JSON-RPC to the worker and gets back the same change set (`pattern`, `objectsReplaced`, `measurements`, `history`, `file`, `view`), which it passes to listeners as the desktop's `AddListener` does. The engine's editor server listens to its document and gathers the changes; `editor_changes` gives what gathered since it last answered, with the undo and redo names and the modified flag, and the worker asks after each call, so every answer is followed by its changes without the API's replies changing shape. Every call is asynchronous; during a drag only the latest request counts and older answers are dropped.
- **Widgets are ours.** A small control base wraps a DOM element, standing in for the LCL's `TCustomControl` and `TPanel`; the list grid is our own on a table. Nothing from npm in the shipped editor.
- **No `Free`, but listeners are removed** when a panel goes, through a `dispose` method, so a closed panel is never kept alive by the document.
- **Shared tables come from the engine**, not copied: shortcuts, commands and their captions are read from it as JSON, so the two editors cannot drift. User-visible text sits in one strings module, as `resourcestring` on the desktop.

## Server

Django serves the editor and `.wasm` file, accounts (with the admin as back office), subscriptions and simple pages as templates. It stores no patterns or measurements and runs no engine jobs. Its own packages are kept to what the job needs and locked, and nothing they use reaches the engine.

**What a subscription pays for.** The engine and editor are GPL and run in the browser, so anyone may host a copy; a subscription cannot sell the program, only what the site adds. That is our own library of blocks and patterns, drafted by us and licensed apart from the code (pattern files are data, not part of the program); use of the Claude assistant, whose API calls cost money per use, passed through the server and not kept (measurements in a prompt are still processed, so the privacy notice says so); and official builds and support. The first web version is the editor alone; subscriptions come once it works.

**Licence.** The engine and editor sent to the browser are distributed, so GPLv3 applies and the source is offered. The Django server is not distributed, so GPLv3 does not require publishing it (the project does not use AGPL), and it does not link the engine. To be checked with a lawyer before the service is sold.
